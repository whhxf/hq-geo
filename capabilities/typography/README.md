# 排版能力

**排版进系统的意思：把「好看」拆成可核验的数值，机器守能守的，人判剩下的。**

排版有两个载体，规则是同一套：

| 载体 | 产物 | 现状 |
|---|---|---|
| 文章排版 | HTML（站 4 候选 + 成稿） | **已接线** |
| 图片排版 | 底图 + 文字层（像素） | 待接线，渲染引擎已定 Chrome headless |

规则只写真源一份（`rules/typography-rules.json`），两条线共用。

## 为什么进系统

2026-10-07 之前，系统里**零排版部件**。文章线站 4 的「生成 3 个风格候选 HTML」只写在文档里，
没有生成器、没有参数、没有判据——**排版做没做、做成什么样，门禁看不出来**。

排版是「求好」那条腿的一部分。防错那条腿已经闭合（事实包契约、准入校验、23 项测试、148 条 canary）；
求好这条腿原本整个外包给 `dbs`（不可商用、结论不落盘、不进单据），违反宪法第 6 条
（只接受有契约和验收清单的部件）。这个能力是第二条内部求好能力。

## 规则真源

每条规则写明数值、来源、证据等级（按 `AGENTS.md` 的六档）和采集日期。

| 来源 | 内容 | 证据等级 |
|---|---|---|
| W3C clreq（中文排版需求） | 避头尾四级、中西文混排 ≤ 1/4 em、行尾点号悬挂、连续标点 2 字宽 → 1.5 字宽 | 官方规则 |
| WCAG 2.1 AA | 对比度 4.5:1（正文）/ 3:1（大字） | 官方规则 |
| Bringhurst | 西文行长 45–75 字符 | 经验模式 |
| 中文排版实测参数 | 行距、字距、行宽 25–35 汉字、缩进与段距互斥、max-width 650–750px | 经验模式 |

**来源必须是可核验的数值，不是审美判断。** 「这样更好看」进不了规则文件。

| TY-03 | 标题行距 | 1.1–1.4 倍 | 1.0–1.5 | 实测参数 |

## 两类判据

- **机器能判的** → `check_layout.py`。数值、范围、互斥关系、对比度。
- **机器判不了的**（读得下去吗、层次清楚吗、风格配内容吗）→ 契约里的 `human_review` 由人填。
  **校验器只守「有没有登记、有没有留 unknown」**——它判不了审美，所以它要求人判留下痕迹。
  没登记是 warn，登记了但没过是 fail。

这条分法和系统两条腿一致：数值能守的机器守，审美只能人判并留痕。

## 用法

```bash
# 判一份排版参数
python3 capabilities/typography/scripts/check_layout.py content/styles/<task-id>.layout.json

# 从 HTML 量出参数，并和声明比对
python3 capabilities/typography/scripts/extract_html_layout.py content/styles/<task-id>.html \
  --compare content/styles/<task-id>.layout.json
```

**参数是判据的真源，HTML 是参数的可视化。** 先定参数、再过校验、最后渲染，顺序不能反。
反过来就会变成「看着还行就发」。

`extract_html_layout.py` 量不出来的值一律填 `null`，**不猜**。校验器把 `null` 判为「没填」，
不判为「合格」——**认不出不等于没问题**。

## 接线

文章正式渲染使用 `templates/article-render.html`；`article.html` 是静态排版金样本，
不得当成可填充模板。渲染器必须把传入正文、字号和来源链接写入最终页面。

**文章线（已接）**：站 4 生成风格候选时，每个候选配一份 `.layout.json`，过 `check_layout.py`；
HTML 写完后过 `extract_html_layout.py --compare`。两条都过才进站 5。

**图片线（待接）**：封面 `cover_text` 的排版走同一份规则。渲染引擎定 Chrome headless——
CSS 本身就是排版语言，一份规则能同时落进文章和图片，且 Chrome 已是 `ego-browser` 的前提，
不新增依赖。渲染与合成脚本等封面排版重复到第三次再做（宪法第 8 条）。

## 实测发现

判据不是凭空写的。下面两条是 2026-10-07 用校验器和逐字渲染**量出来**的，
都直接改变了做法。

### 一、风格库的点缀色不能当小字用

量 `image-styles.json` 里 `editorial-minimal` 的配色，压在它自己的米白底 `#FAF8F3` 上：

| 角色 | 色值 | 对比度 | 能当什么 |
|---|---|---|---|
| `text` | `#2B2926` | **13.67:1** | 正文、标题都行 |
| `accent` | `#E2603A` | **3.32:1** | **只能当大字（≥24px 或粗体）或装饰线，不能当小字** |
| `muted` | `#8C8781` | **3.35:1** | 同上 |

风格库把 `accent` 定义成「单一信号色点缀」——它本来就是给细线和色块用的。
但之前没有任何东西拦着，`accent` 可以被填进 `cover_text` 的字色里，然后封面上的小字读不清。

**要用点缀色做字，得换一个更深的同色相**：`#993C1D` 是 6.55:1，能当阅读文字。

### 二、风格库引用的字体本机没有

TypeSpec 有一格 `font_family`（落到 CSS 的字体栈）。逐字渲染比对，本机实测：

| 风格库引用的字体 | 本机 |
|---|---|
| 思源黑体 / Source Han Sans / Noto Sans CJK | **没有**（静默回退成宋体） |
| 思源宋体 / Source Han Serif | **没有** |
| 站酷快乐体 / ZCOOL KuaiLe | **没有** |

| 本机可用的中文字族 | 类型 |
|---|---|
| PingFang SC | 无衬线（在 `/System/Library/AssetsV2/` 的字体资源里，不在 `/System/Library/Fonts/`） |
| Hiragino Sans GB | 无衬线 |
| Heiti SC / STHeiti | 无衬线 |
| Songti SC | 衬线 |

**后果：风格的名义字体和实际字体不一致，而且没有任何信号。** 风格库写「思源黑体 Heavy」，
渲染出来是 PingFang；写「站酷快乐体」，渲染出来还是 PingFang。排版参数全对，字却不是你选的那个。

**这一格现在没有校验器守。** 要不要给风格库补一份「字体可用性」检查，等图片线接线时一起定——
它属于风格（`image-production/styles/`），不属于排版参数。

## 已知边界

- 文章 Markdown 引用链接须渲染为可点击链接；只允许 `http`、`https` 和相对路径，拒绝脚本协议。

- **提取器只认简单选择器**（`tag`、`.class`、`*`）。`article p` 这类复合选择器读不到，
  `@media` 块不解析。**读不到就是 null，不会误报为合格。**
- **`line_break_level` 的映射是近似的**：CSS `line-break` 的 `normal → gb`、`loose → basic`、
  `strict → strict`、缺省 → `none`。校验器只要求级别显式声明且合法，不要求 CSS 与 clreq 逐条对齐。
- **`cjk_latin_spacing_em` 从 CSS 自定义属性 `--hq-cjk-latin-spacing` 读**，缺省 0。
  CSS 没有直接表达中西文间距的标准属性，所以走显式声明。
- **不判渲染结果**。校验器判参数，不截图量像素。封面线的图文关系（文字压到主体上、
  对比度被底图吃掉）要在图片线接线时另做判据。
