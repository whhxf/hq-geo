# 调研结论备查库

**回答：一轮调研做完，什么是值得留的，留在哪，怎么留。**

## 为什么要有这一层

关键词研究是这条链路里**最贵的一步**。一次 SERP 研究是 每个词 × 每个平台 各一次采集；
商业工具的拓词任务是异步作业，提交完要等十几分钟才有结果。**结论只留在对话里，下一轮就从零开始——
那等于这次白花。**

已经有的三处存储，都不是给「以后查」用的：

| 已有 | 是什么 | 为什么不能当备查库 |
|---|---|---|
| `research/raw/` | 一次采集的全部信号 | **不改写、不带判断**。它忠实，所以它没法回答「所以呢」 |
| `research/normalized/` | 这一轮聚出来的需求簇 | **绑定当轮问题**。换一个问题，同一批数据要重新聚一次 |
| `topics/` | 备选选题 | 是**承诺**不是发现——要答得出五问才进得去 |

缺的是**跨轮次、给人看、随手可查**的那一层。

## 落在哪

```
research/library/<主题>.md
```

文件头记主题和两个日期，正文按结论分节：

```markdown
---
topic: <主题>
covers: [<这个词>, <那个词>]
summary: <一句话说清这个文件里最值钱的判断>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

**`covers` 和 `summary` 是索引的来源，必填**——索引由它们生成，见下一节。
`updated` 是**复核的痕迹**：一条结论半年后重新采过、还成立，就动这个日期，不用改正文。

**一个主题一个文件，文件名不带日期。** 日期在文件头的 `created` / `updated` 里。

- **为什么不是一个大文件**：主题各自生长。三个月后它变成一份没人愿意读的流水账，
  而没人读的库等于没有库。
- **为什么不是一个结论一个文件**：同一主题的结论**要放在一起看才有意义**——
  互相印证还是互相矛盾，分开就看不出。
- **为什么文件名不带日期**：库里是**累积**的，不是一轮一份。`raw/` 和 `normalized/` 才是一轮一份。

## 索引：让库**被找出来**，而不是等人想起来

**建了库但没人知道该翻哪一个，等于没建。** 数据一多，「它记在哪」这件事依赖记忆，
而记忆会失效——于是花了钱采的结论躺在那里没人用，下一轮从零开始。
**这正是建这个库要解决的问题本身，不能在库里原地复发一次。**

### 索引是派生的，不是手写的

两处索引都由脚本从库文件的 front matter 生成：

| 位置 | 什么时候进上下文 |
|---|---|
| 项目根 `CLAUDE.md` 的 `<!-- library-index:start -->` 块 | **会话启动即注入**，不用谁想起来去读 |
| `research/library/README.md` | 有人翻这个目录时 |

```bash
python3 capabilities/keyword-research/scripts/library_index.py --project <项目根>
```

**为什么必须是派生的**：手写的索引一定会漂移，而**漂移的索引比没有更糟**——
它会让人以为「库里就这些」。校验器因此不是「检查索引格式」，而是
**按生成器重算一遍、逐字比对**。人忘了重生成，门禁就红。

### 每个库文件必须写 `covers` 和 `summary`

```yaml
covers: [AI数字员工, AI客服, 智能体搭建]
summary: 一句话说清这个文件里最值钱的判断
```

**`covers` 是覆盖的词，不是主题名。** 主题名和词的对应关系不是一对一的——
`AI客服` 的结论住在 `AI数字员工.md` 里，因为它们是同一门生意，放一起才看得见
彼此印证或互相矛盾。**没有这一列，按词就搜不到。**

**所以找的时候按词搜「覆盖的词」列，不要按主题名猜。**

### 校验器拦的第三件事：调研做完了但没入档

`research/normalized/` 里出现过的核心词，必须在某个库文件的 `covers` 里。
拦不住的话，「花钱采了但没留下」会静默发生——比不做还糟，因为不做会有人问，做了没留不会。

## 什么进库

**两条都答「是」才进：**

1. **半年后还成立吗？**
2. **别的选题会用到吗？**

| 进 | 不进 |
|---|---|
| 跨平台需求强度差异（同一个词在两个生态差多少） | 这个词今天排第几（会变） |
| 一个簇被第二个平台独立复现 | 这一轮聚出的簇列表本身（那是 `normalized/` 的事） |
| 某类词有量 / 没量的**判断** | 没跑通的渠道的原始报错 |
| 口径本身的发现：某字段平台全空、某标度的上限 | 「我觉得这个方向行」 |

**判断法：这条结论换个主题还能不能用？** 能 → 进库。

## 每条结论必须带三样

```markdown
### <一句话结论>

- **数字**：……
- **口径**：这条在什么条件下成立，什么时候不能用
- **出处**：`research/raw/<文件>`，采集于 YYYY-MM-DD
```

**三样缺一不可，缺哪样这条结论就不该进库。**

- **没有口径的数字是错的，不是不完整的。** 库里一个裸数字被引到内容里，就成了跨平台加总——
  `AGENTS.md` 第 61 行是硬线。**口径不是免责声明，是数字的一部分。**
- **出处必须指到文件，不能只写「小红书」。** 结论会活很久，`raw/` 会被清理、平台会改版。
  半年后要复核一条结论，得能直接翻回原始记录。
- **采集日期不是形式。** 平台口径会变——2026-09-29 的量级不能当成 2027 年的量级。
  写日期是让下一个人知道这条**该不该重新采一次**。

## 推翻要留痕，不要删

结论被证伪时**划掉 + 写明什么时候、被什么推翻**：

```markdown
- ~~搭建类词没量~~（2026-09-29 推翻）：聚光交叉验证显示 `数字员工搭建` 有量。
  原判断只看了广点通一个生态，见 `research/normalized/<文件>`。
```

**「这个假设是错的」本身就是参考资料。** 删掉的话，半年后的自己会重新踩一遍——
而且因为库里干干净净，会以为自己没想过这个问题。

## 和 `LEARNING.md` 的分工

| 文件 | 记什么 | 判断法 |
|---|---|---|
| `research/library/` | 这次**市场**是什么样 | **能不能直接写进一篇内容里？** 能 → 进 library |
| 项目根 `LEARNING.md` | 这次**做法**要改什么 | 不能，且指向某个具体动作 → 进 LEARNING |

一个是**发现**，一个是**教训**。「我发现 X」进 library，「我下次该 Y」进 LEARNING。

## 边界

- **工具级口径进渠道文件，不进库。** 「这个字段平台全空」「这个标度的上限未核实」跨项目成立，
  属于 `capabilities/keyword-research/channels/<渠道>.md`。库里放的是**本轮这批数据**为什么不能那么比。
  混起来，库会退化成渠道文件的第二份拷贝，两边各自过期。
- **不进事实包。** 库里是平台信号，不是事实——要事实走 `capabilities/sourcing/` 的检索路径。
  这一条和 `research/` 整体一致：**别因为它是「结论」就以为它比原始记录硬。**
- **不写没出处的东西。** 没采过的判断不进库。
- **不把快照当结论。** 「今天谁排第一」是快照，不是结论。快照会自己过期，结论不会。
