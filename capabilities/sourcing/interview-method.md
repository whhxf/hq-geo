# 访谈：怎么问

取材的访谈路径。目标是**把 brief 的格子一格一格填满**，材料从用户脑子里来。

## 这一环问什么

不是「聊天」，也不是「写稿前的暖场」。每一问都要能回答一句话：

> **这个回答会填上哪一格？**

填不上的不问。这就是这一环的全部纪律，下面所有判据都是它的展开。

**格子有三处**：

| 格子 | 在哪 | 例 |
|---|---|---|
| brief 的字段 | `production-brief.schema.json` | `objective`、`audience`、`core_thesis`、`script[]`、`required_assets[]`、`prohibited_claims[]` |
| 事实包的 owner 四类 | `capture_fact.py` 的 `ALLOWED_OWNER_CATEGORIES` | `founder_viewpoint`、`firsthand_experience`、`internal_process`、`product_intent` |
| 选题的字段 | `topics/<idea>/topics.json` | `title`、`pillar`、`angle`、`proof` |

开始前先把空格列出来。**列不出来就说明还不知道要做什么**——先问一个能定方向的问题。

## 一次只问一个

站 2 已有这条，这里写清为什么：**一次问三个，用户只会回答最容易的那个**，
另外两个会永远拿不到，而你以为问过了。

一轮只推进一件事。用户答完，再决定下一问。

## 每一问之前，先在内部锁定五件事

```
当前对象：用户刚才提到的哪个具体对象
待补缺口：事实 / 判断 / 因果 / 边界 / 例外 —— 是哪一种
提问动作：描述 / 区分 / 比较 / 解释 / 判断 / 选择 —— 只取一个
判断维度：本轮只沿哪个维度推进
填哪一格：回答会落进上面三处格子的哪一个
```

**五件事任一不清楚就不发送。** 尤其是最后一条——想不出填哪一格，说明这一问是在凑对话。

**问之前把问题写出来，自己读一遍**：里面有没有两个对象、两个动作、两个维度？
有就拆成两轮。抽象词指代不明（「它」「那个」）就改回用户自己用过的具体名词。

**用户说没看懂时，上一问作废。** 撤回，找出是对象、动作、指代还是维度出了问题，
用具体名词重问一个。**不要解释原问题，不要追加例子或选项**——那是把失败推给用户。

## 用户说不清时，四个换法

这是访谈路径的核心技术。用户说「我也说不太清楚」不是终点，是**换入口的信号**：

| 换法 | 怎么问 |
|---|---|
| **还原事件** | 「你最近一次遇到这种情况，是什么时候？当时从头到尾是怎么发生的？」 |
| **追问信号与动作** | 「你当时看见什么，让你决定这么做？你排除了哪些做法？」 |
| **比正反案例** | 「有没有一次是做成的？那次和这次差在哪？」 |
| **问失效边界** | 「什么情况下这个判断不成立？」 |

四个入口轮流试。**还不出来就保留为未知，不要提供候选答案让用户认领。**

> 「是不是因为客户更信任视频？」——**这是喂答案**。用户会顺着说是，然后这条事实就是假的。
>
> 「那次客户问了你什么？」——**这是取材料**。用户答什么就是什么。

## 不许问的

- **「是不是因为……」**「会不会其实是……」——把因果假设塞进问题
- **给选项**：「是 A 还是 B？」——除非 A 和 B 都是用户自己说过的
- **替用户建分类**：「这属于产品问题还是信任问题？」——分类是你的工作，不是他的
- **认领式提问**：「你觉得这个说法对不对？」——他会说是

判据：**问题里除了用户已经说过的词，还有没有你新加的词？** 有新加的，就是诱导。

## 挖到的东西分两路落

用户答完，**先判断这一条属于哪一类，再决定落到哪**：

| 用户说了什么 | 落到哪 | 用什么 |
|---|---|---|
| 对某件事的判断、立场、取舍理由 | 事实包，`founder_viewpoint` | `capture_fact.py` |
| 他亲历的一件事（时间、动作、结果） | 事实包，`firsthand_experience` | 同上 |
| 内部怎么做事的流程 | 事实包，`internal_process` | 同上 |
| 产品为什么这么设计 | 事实包，`product_intent` | 同上 |
| 外部效果、客户评价、同行数据 | **不能进 verified** | 见下 |
| 直接就是 brief 某格的内容 | `production-brief.json` | 手写 |

**外部效果那一条要特别小心**：用户说「我们客户用了效果很好」，这是 `company_claim`，
不是 `verified` 事实。校验器会拒绝——`owner_statement` 只能验证四类 owner 事实。
真要写进内容，得先找到能支撑它的外部证据（走检索路径）。

## 原话必须留

**逐字保存，不改写。** 存进 `research/interviews/<date>-<slug>.md`，按轮次记：

```markdown
## T003
**问**：那次客户问了你什么？
**答**：（用户原话，一字不改）
**落**：fact `kv-q-response` → `founder_viewpoint`
```

「逐字」只指收到的文字，不代表和录音核对过。

**为什么不能改写**：事实条目里的 `claim` 是你提炼的原子陈述，`answer` 必须是原话——
以后有人问「这条事实哪来的」，要能指回原话。改写过的「原话」回指不了任何东西。

**内部分析不写进访谈记录。** 你判断这条属于哪一类、为什么这么问、下一问打算问什么——
这些留在执行上下文里，不进记录。记录是采访事实的真源，不是操作流水账。

## 旁支：先记，不打断

用户说到一条能独立成篇的线索（一个故事、一个反常判断、一个他没展开的机制）时，
**一句短提示 + 记下来，继续当前主线**：

> 「这里有一条值得单独聊的：你说准备得越完整反而越难开始。我先记下，当前先把主线说完。」

旁支攒到收束时一起给用户选。**不因为旁支有趣就切换主线**——那会让当前 brief 永远填不满。

## 什么时候停

主线填得差不多了（brief 的空格补上大半、关键边界没有明显缺口）时，**先进入候选收束，不能直接结束**。

**两问，分两轮问，不能合并**：

1. **内容有没有遗漏、我没问到的？**
2. **你自己还有没有没想清楚的地方？**

第一问让用户回顾覆盖了什么，第二问允许他从自己还没琢磨清楚的地方开口。**两句不能互相替代**——
用户只说「没有补充」时，下一轮只补问第二问，不重问整套。

用户答完两问，或者明确说暂留，**才冻结这一轮**。然后：

3. 列出旁支，问：「你想现在继续哪一条，还是先留到以后？」

**收束确认和旁支选择必须分成两轮**——合并成一问，用户会只回答其中一个。

**不做「阶段末补缺清单」。** 会让当前结论站不住的决定性缺口，在主线还在走的时候就该问，
不留到最后集中补。攒到最后一起问，等于承认前面每一问都没想清楚。

## 访谈结束不等于创作结束

收束后交出去的是：填到一半或填满的 `production-brief.json`、新落的事实包条目、访谈记录、旁支清单。

**brief 的 `status` 按实际情况写**：还有格子空着就是 `draft`，有硬缺口（素材没有、
事实没确认）就是 `blocked`——**不要为了让流程往下走就标 `ready_for_production`**。
素材和界面都还没到位的 brief 卡在 `blocked` 就是对的。

## 已知的坑

- **不要问「你想说什么」**——那是把组织工作推回给用户。要问「你上次遇到这事是什么时候」，
  问的是**具体的事**，不是让他总结。
- **不要在用户卡住时给建议**。给建议他会顺着走，然后你拿到的是你的观点，不是他的。
  换四个入口里的另一个，还不行就记未知。
- **不要一次问完所有空格**。列空格是给你自己看的，不是给用户的问卷。
- **用户答得短不代表没内容**。「嗯，是这样」后面往往还有——追问「能举个例子吗」，
  但**只追一次**，第二次还短就换入口。
- **访谈记录不要写成对话小说**。只存问和答，不存你的思考过程。
