# 功能测试与发布门禁

只有一个入口，**必须指定项目**：

```bash
python3 test/run_quality_gate.py --project <项目根>
```

在项目根里跑时可以省掉 `--project`。全部测试一秒内跑完，所以不分档。分档只会让人挑便宜的那档跑，然后误以为通过了门禁。

只验证当前改动影响到的能力：

```bash
python3 test/run_quality_gate.py --project <项目根> --changed
```

`--changed` 用于缩短反馈时间，不能替代完整门禁。改动落在规则文档或 `test/` 自身时，它会自动退化为全量运行——那种情况下影响面无法局部判断。

## 增加或修改功能

1. 在 `test/feature_registry.json` 登记功能，先用 `planned`。
2. 实现测试并在 `test/test_manifest.json` 登记命令。
3. 把测试 ID 绑定到功能，再将状态改为 `partial` 或 `implemented`。
4. **跑 canary**，确认新断言不是空转的（见下节）。
5. 运行 `python3 test/run_quality_gate.py --project <项目根>`，并在**至少两个项目**上各跑一次——只在一个项目上跑，证明不了方法可复用。
6. 只以 `test/reports/<项目名>/latest.json` 的 `verdict` 判断是否通过。

新增功能没有测试、已实现能力引用不存在的测试、责任路径消失，都会被门禁阻断。修 Bug 时测试应先复现失败，再验证修复；删除能力时应增加断言证明入口、路由和副作用均已消失。

## 测试自己会不会是假的

会。一条写错的断言可以永远是绿的——看着像守住了某件事，其实什么都没守。**空转的断言比没有断言更糟**，因为它给的是虚假的信心。

光读代码看不出来，唯一可靠的办法是把它依赖的那行删掉，跑一遍，看它红不红：

```bash
python3 test/tools/canary.py --project <项目根>
python3 test/tools/canary.py --project <项目根> --only 站6   # 只跑匹配的那几条
```

破坏点写在 `test/canary.json`：**改了断言就加一条**，否则新断言可能一出生就是空转的。一条破坏点可以跨多个文件——去掉一个概念，要在它出现的每个地方都去掉。

这个工具**不进日常门禁**（它故意把文件改坏再还原）。它是写断言的人的工具，用在写完之后、提交之前。它自己的核心逻辑（替换所有出现、失效检测、不改原文）由 `canary-unit` 守着。

**写断言的规矩**：断言**整行定义**，不是关键词是否出现。关键词在同一节里往往出现多次，删掉定义行还剩一次，断言照样绿——2026-09-28 第一次跑 canary，9 条里 5 条是这么被发现的。

## 冻结的功能

不打算继续维护但暂时保留代码的功能，登记在 `test/feature_registry.json` 的 `frozen` 字段，写清路径、冻结原因和恢复条件。冻结项不进门禁，也不占用覆盖率分母。

## 报告

- `test/reports/<项目名>/latest.json`：机器读取的唯一结果真源。按项目分开，混在一起就看不出系统在哪个项目上更有效。
- `test/reports/<项目名>/latest.md`：给人看的摘要和错误详情。

代码变化后，旧报告自动失去发布参考价值，必须重新运行门禁。
