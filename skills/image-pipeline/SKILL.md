# 图片流水线

## 目的

从一条任务出发，产出一组**能说清自己是什么**的图。

**这条线强依赖 AI 生成，不做图片编辑。** 没有图层、没有涂抹、没有局部修改——
做的是把「要什么」说清楚，组装 prompt，调模型一步出图。
用户要改一张已有的图，直说这条线不干这个。

**先分流：生成图，还是示意图。**

| 要什么 | 走哪 |
|---|---|
| 照片、插画、氛围图、场景图 | 本线主路，调模型出图 |
| 示意图、流程图、架构图、时间线、图表 | 信息图生产线 `capabilities/diagram-production/README.md` |

**示意图不走本线。** 它不调模型，产物是自包含 HTML 加内联 SVG。
本线五站的判据是给生成图写的。套到示意图上，只会逼着模型去画流程图——画出来全是错的。

## 开始前

完整读取：

- `capabilities/image-production/contracts/image-brief.schema.json`
- `capabilities/image-production/styles/image-styles.json`——**不要凭记忆背风格清单**，以文件为准
- `capabilities/content-production/styles/README.md`——风格「看样选」的机制

读项目根的 `tasks/<id>.md`、`facts/`、`topics/`。图片简报住在
`content/briefs/<idea>/<topic>/image-brief.json`，和视频简报同一个位置。

**先看这个选题是不是已经有图片简报**，有就接着改，不新建第二份。

## 五站

### 站 1 · 读任务，查事实

从任务单里读出：这条内容对谁讲、核心判断是什么、要发在哪。

**平台决定尺寸，用途决定构图，核心判断决定画面上能出现什么。** 三样缺一样就不要往下走。

查事实包：这张图要表达的东西，有没有 `fact_refs` 撑得住？
撑不住的先回站 2 补料，不要先画出来再说——**画出来之后你会舍不得删**。

### 站 2 · 写图片简报

按 schema 写 `image-brief.json`。**先写 `deck`，再写每一张。**

**一组图是一个整体，不是十张单图。** 2026-10-08 之前简报只描述单张图，
于是四条**组层面**的判据无处落地——全套共用一个风格、封面从内页里隔离出来、
序号与总数、末页落点。这四条单看任何一张都看不出问题，只有整组一起看才看得出来。

`deck` 四格（交付物 ≥2 张时必填）：

| 字段 | 要回答的问题 |
|---|---|
| `style_id` | 全套共用哪一个风格。每张交付物的 `style_id` 都要等于它 |
| `sequence_total` | 一共几张。必须等于交付物的张数——对不上，读者看到的进度就是假的 |
| `cover_theme` / `inner_theme` | 封面和内页分别用哪套底色。**必须不同**（隔离效应，AP-04） |

逐张图填：

| 字段 | 要回答的问题 |
|---|---|
| `role` | 这张图在内容里干什么用（封面 / 配图 / 步骤示意 / 对比）。**封面那张必须含 `cover` 或 `封面`**——校验器靠这个词认出封面，认不出就不会要求它带封面文案 |
| `size` | 发在哪，什么尺寸 |
| `subject` | 画面里有什么。**写具体的物和光，不写形容词**——「米白色桌面、柔和侧光、浅阴影」，不是「高级感」 |
| `subject_kind` | 这张图画的是**概念**，还是**声称真实存在的东西** |
| `synthetic` | 是不是模型生成的。**必须显式写** |
| `source_assets` | 素材哪来的，权利状态 |
| `claims_on_image` | 图上出现的每一句**事实主张**，逐条挂 `fact_ref` |
| `cover_text` | 封面要排的**文案**（题目与钩子），挂 `source_title`、不挂事实。**封面必须有这一格** |
| `points` | 图上**并列展示的短句**，最多 3 条（AP-07）。超过三条，一眼扫不完就变成「要读」，而读者不读 |
| `sequence` | `NN/NN`（第几张 / 共几张）。有 `deck` 时每张都要写（AP-06） |
| `base_image` | 封面的**底图**。风格库 `carrier` 是 `base_image` 的风格，封面必须有这一格（AP-02） |
| `base_image_rights` | 底图的权利状态。有 `base_image` 就必须写 |
| `next_step` | **末页**给读者的具体动作（AP-09）。「欢迎咨询」不是落点——它不是动作。简报进 ready 时才要求 |
| `reference_images` | 参考哪几张（用户给了喜欢的图时才有） |
| `reference_instruction` | 参考它的什么。有 `reference_images` 就必填 |
| `palette_ref` | 量出来的色板文件，出图和回测共用这一份 |
| `status` | 这张图能不能出 |

**顶层还要写 `author`**——写这份简报的是谁。它唯一的用途是分离职责：
复核吸引力的人必须不是写的人（见站 5）。

**`subject_kind` 是这份简报最重要的一格。** 它决定这张图能不能由模型生成：

- `concept`——概念图、氛围图、示意。模型生成没问题。
- `product_ui` / `customer_case` / `real_conversation` / `real_person`——**声称真实存在的东西。**
  这四类不能生成。模型画出来的界面按钮位置、字段名全是编的，看图的人会以为那是真的产品。

用户说「画一张我们的产品界面」时，**不要直接画**，告诉他：界面要真截图，模型会编；
要的是概念图的话，改 `subject_kind` 为 `concept`，画面上就不出现具体界面。

**图上有两种文字，分开走，别混。**

| 走哪条 | 挂什么 | 是什么 |
|---|---|---|
| `claims_on_image` | `fact_ref` | **事实主张。** 图上写的字和正文一样要能被追问出处；挂不上事实的，从图上拿掉 |
| `cover_text` | `source_title` | **封面文案。** 这篇文章或这个商品的题目与钩子——它不承诺效果，所以不挂事实，但必须写清取自哪条标题 |

**封面必须有 `cover_text`。** 一张无字的封面在一屏几十条的流里不会被任何人看见。
2026-10-07 的实例：封面出了明亮通透、线缆整齐平行排布的静物照，无文字、无冲突、无情绪，
而标题押的是「乱」——**封面给的「整齐」和标题的「乱」正好反向**，扫到的人看不到自己。

字段名对齐风格库 `sample` 里的 `headline` / `kicker` / `meta` / `layout`：

| 字段 | 要回答的问题 |
|---|---|
| `headline` | 主文案。**必须有**，且必须是一句读得懂的话——关键词照抄不算 |
| `source_title` | 取自哪条标题。**必须有**。写不出取自哪里，它就是一句新编的、没人认领的承诺 |
| `kicker` / `meta` | 小字标签、一行出处。可省 |
| `layout` | 文案落在画面哪个位置。取值必须在风格库某套 `sample.layout` 里出现过——文案压住主体是封面最常见的废掉方式 |

**封面文案不挂事实，但它不是免责的。** 它不得承诺效果、不得出现 `prohibited_claims`
里的任何说法——「效率提升 300%」写成标题一样是假主张，只是换了个地方说。

**文案怎么上封面：走 A 方案。** 底图由模型生成，文字用**真实文本渲染**叠上去——
文字清晰可控，改字不用重出图。**排版环节目前还没进系统**（合成脚本要依赖 PIL，
而系统根只用标准库），当前由外部工具合成，产物落在项目根 `assets/composed/<brief-id>/`，
与模型直出的 `assets/generated/` 分开，两边的图不许混着数。
B 方案（让模型直接画字）不走：中文大概率糊字，且改一个字要重出一张图。

### 站 3 · 选风格

**风格靠看，不靠读。** 不要凭风格名推荐，不要跳过预览直接生成。

从 `image-styles.json` 里按 `platforms` 和 `best_for` 筛出 3 个候选，
用每个风格自己的 `sample` 字段生成真实样张，并排给用户看。用户选完写回每张图的 `style_id`。

**一套图共用一个 `style_id`。** 风格漂移（同一组图里有的米白有的深色）是成套图最明显的破绽。
写回 `deck.style_id`，每一张交付物的 `style_id` 都要等于它。

**`carrier` 决定封面要不要底图。** 风格库里每套风格都写了 `carrier`：

| `carrier` | 意思 | 封面要什么 |
|---|---|---|
| `base_image` | 画面主体是一张图（照片、插画、矢量图形、界面截图都算） | 必须有 `base_image`（AP-02） |
| `typography` | 画面主体是字（纯文字排版） | 不需要底图，封面靠与内页的底色差异隔离（AP-04） |

14 套里 13 套是 `base_image`。**照着风格名选、然后排一张纯文字的图出来，是最容易犯的错**——
2026-10-08 那次就是这样：选了 `editorial-minimal`（它的样张是一张俯拍静物照），
实际交付的是米白底加居中文字，一张底图都没有。

**不做风格自动选择。** 风格靠看，不靠读——脚本只提供筛选用的字段，最终选择由人做（宪法 7）。

用户对某张图有特殊要求时，改的是 `subject` 和 `intent`，**不是换风格**。

#### 用户给了参考图时

用户说不清自己喜欢什么，但能给出喜欢的图。**不要让他描述**——
让他把图放进项目根 `assets/reference/`，然后量出来：

```bash
python3 capabilities/image-production/scripts/measure_palette.py \
  <项目根>/assets/reference/图.png -o <项目根>/assets/reference/palette.json
```

量出来的色板是**数字，不是形容词**。它同时喂两个下游：出图时的 `color_palette`
参数，和站 5 回测时的预期色板。同一个文件，不转译——转译就是信息损失。

三条判据：

- **`role` 是猜的，`hex` 和 `coverage` 是量的。** 一张纯蓝渐变里没有文字色，
  脚本仍会把某个蓝标成 `text`。**不要把 role 当成「这张图真有这六种角色」的证据**，
  它只是让色板可读。
- **一套参考图量一次，全套图共用。** 逐张图分别量会让同一组图各带各的色板，
  那就是另一种风格漂移。
- **量出来的色板不写进 `image-styles.json`。** 那是判断，不是测量——
  要不要沉淀成新风格由人决定（宪法 7）。

参考图大概率不是自己拍的，进项目根就要登记来源与权利，
并且**只用于内部测量与出图条件，不进入任何对外产物**。

### 站 4 · 出图

先读取 `capabilities/image-production/runtime-discovery.md`。运行时先检查当前会话是否实际暴露系统生图工具；有则直接由 Agent 调用，不默认使用下方固定 API。没有系统工具才检查本地生图 Skill 的可执行性；都没有则问用户提供能力或素材。下方 `generate_image.py` 是已明确选用该供应商时的适配器，不是默认入口。无论使用哪个提供方，事实准入、图片简报、生成记录和独立复核要求相同。

先 dry-run 看组装出来的 prompt：

```bash
python3 capabilities/image-production/scripts/generate_image.py \
  --brief <项目根>/content/briefs/<idea>/<topic>/image-brief.json --dry-run
```

**把 prompt 念给用户听一遍再出图。** 出图要花钱，而 prompt 里写错一个词，
四张图一起错——先看后做比先做后改便宜。

**dry-run 会连参考图和色板一起打出来，它们也是在 dry-run 阶段读的。**
这是有意的：参考图路径写错、色板文件格式不对，都必须在**花钱之前**暴露。
出图时才报错，钱已经花了。

用了参考图时，简报里那张图必须写两个字段：

| 字段 | 要回答的问题 |
|---|---|
| `reference_images` | 参考哪几张（项目根相对路径，落在 `assets/reference/` 下） |
| `reference_instruction` | **参考它的什么**。一句话 |

`reference_instruction` 不是可选的：万相 2.7 的多图参考是**生成 + 编辑**模型，
不说清参考什么，它可能把参考图当成待编辑对象——你拿到的就是「改了一下的参考图」
而不是一张新图。写「只参考它的配色和留白」，不要写「参考这张」。

确认后去掉 `--dry-run` 出图。图落在项目根 `assets/generated/<brief-id>/`，
回执写在同目录的 `manifest.json`。用了参考图/色板的图，回执里多记
`reference_images` / `reference_instruction` / `palette_ref` / `color_palette`——
**没用到的图回执一字不改**，不给旧产物平添噪声。

### 站 5 · 验收

**机器检查 + 人看，两道都要，不能互相替代。**

机器能查的（跑校验器）：

```bash
python3 capabilities/image-production/scripts/validate_image_brief.py
```

- 尺寸和张数对不对
- 该标 `synthetic` 的标了没有
- `claims_on_image` 挂上事实没有
- 封面有没有 `cover_text`，`cover_text` 有没有写清 `source_title`
- 有封面文案时，有没有 `appeal_review`，四项判断有没有留 `unknown`
- 素材权利状态写全没有
- 参考图有说明、路径在项目根内、文件真的在
- `palette_ref` 指向的是一份能用的测量结果

用了参考图的，再跑一次回测——**这是整条链上唯一能机器判否的环节**：

```bash
python3 capabilities/image-production/scripts/verify_palette.py \
  --expected <项目根>/assets/reference/palette.json \
  --actual <项目根>/assets/generated/<brief-id>/d1.png
```

它把出出来的图重量一遍，跟预期色板比色差（ΔE00）和面积占比，
**配不上就红**。没有它，「像不像」只能靠人看，出十次图人就要看十次。

关于回测的三条：

- **它只测颜色和面积，测不了「这张图配不配得上那句话」。** 回测 PASS
  不等于可以发，构图、质感、有没有混进不该有的东西仍然归人。
- **它按最近色匹配，不按 role 匹配。** 所以「role 标签变了」不会被误报成
  「颜色漂了」——假警报多了就没人看结果了。
- **阈值还没拿真实出图校准**（输出里 `thresholds.calibrated: false`），
  现在能说明的只有「没偏得离谱」。跑够 3–5 次真实出图后再回来收紧阈值。

机器**查不了**的，必须自己看：

- 图上的字有没有糊、有没有错别字、有没有多出没要求的字
- 画面里有没有混进不该有的东西（别人的 logo、真实人脸、错误的品牌色）
- 这张图**配不配得上那句话**——图好看但和核心判断无关，是废图

#### 吸引力：机器判的数值，人判的登记

机器能判「合规」，判不了「有人点」。但**「有人点」不是完全测不了**——
2026-10-08 之前这条线五站全是事实纪律，每一站都在回答「这张图有没有骗人」，
没有一站回答「有没有人愿意看」。结果是十张图交付，Conan 看完说
「比较素，让人没啥阅读兴趣」。

**吸引力分成两半：机器判的数值，人判的登记。** 两半都要，不能互相替代。

##### 一、机器判的数值：`check_appeal.py`

判据真源在 `capabilities/image-appeal/rules/appeal-rules.json`（十四条，AP-01 至 AP-14）。
执行者是 `capabilities/image-appeal/scripts/check_appeal.py`：

```bash
python3 capabilities/image-appeal/scripts/check_appeal.py \
  <项目根>/content/briefs/<idea>/<topic>/image-brief.json
```

它判九条：封面标题长度、封面视觉承载体、封面底图复杂度、封面与内页隔离、
全套单一风格、序号与总数、单页要点上限、末页落点、文案机器化模式。
**阈值全部从规则文件读，不在代码里另写数字。**

**「素」是可测的。** 它有一个代理指标：整张画面只有一个视觉事件。
`capabilities/image-appeal/scripts/measure_card.py` 量三个数：

```bash
python3 capabilities/image-appeal/scripts/measure_card.py <封面底图.png>
```

| 指标 | 意思 | 实测（2026-10-08） |
|---|---|---|
| 色数 | 4 位/通道量化后还剩几种颜色 | 被否的纯文字卡 59–63；有承载体的图 322 |
| 边缘密度 | 相邻像素亮度差 >24 的比例 | 被否的卡 0.028–0.047；有承载体的图 0.067 |
| 主色占比 | 最大明度带占多大 | 被否的卡 0.948–0.968（九成五是同一个明度） |

阈值取两组之间的间隙，写在 AP-03 里。**它量的是封面底图，不是合成后的成品卡**——
成品上叠了文字，文字的边缘会把数字抬上去，「底图是一块纯色」这个事实就被自己的标题掩盖了。

**阈值还没校准。** AP-03 的样本是 10 比 1（十张被否的卡 对 一张真实截图），
`calibrated: false`。现在能说明的只有「明显偏素」。跑够 3–5 套真实图集再回来收紧。
引用实测数字时必须带上这个状态，别把它说成合格线。

##### 二、人判的登记：`appeal_review`

`appeal-rules.json` 里标 `checkable: human` 的五条，机器判不了：

| 维度 | 要回答的问题 | 来源 |
|---|---|---|
| `information_gap` | 封面有没有点出缺口但不填（好奇心） | Loewenstein 1994 |
| `unexpectedness` | 这句话有没有打破读者已有的预期（猎奇） | Heath SUCCESs 的 Unexpected |
| `emotional_arousal` | 押的是高唤醒情绪还是低唤醒（情绪价值） | Berger & Milkman 2012 |
| `practical_value` | 有没有一条能立刻用上的具体做法（信息价值） | Berger STEPPS |
| `social_currency` | 读者转它，同事会怎么看他（分享动机） | Berger STEPPS |

**测不了的不假装能测。** 这五条不设机器阈值，只守两件机器能守的事：
该判的时候有没有人判过，判的人是不是独立于写的人。

连同 2026-10-07 定的四项（`same_direction_as_title` / `has_readable_hook` /
`has_conflict_or_tension` / `scannable_in_feed`），一共九项，写进简报的 `appeal_review`，
逐项给 `pass` / `fail` / `unknown`。

**复核的人不能是写的人。** `reviewed_by` 必须与顶层 `author` 不同，
并且要写清 `evidence`——实际看过什么，一句话。

这一条是 2026-10-08 加上的，因为出过事故：写简报的 Agent 自己把四项全填了 `pass`，
十张图交付，Conan 看完说「比较素」。**登记了，质量没守住。**
机器判不了「有没有人愿意看」，但它**能**要求判的人不是写的人——
同一个人写又同一个人判，等于没判。

**九项全 `pass` 才允许简报进 `ready`。** 有一项 `fail`，先改封面再复核；
`unknown` 等于没复核。校验器会拦。

**复核不是照模板填。** `evidence` 写不出看过什么，这份复核就是假的。
可以写：「把封面缩到 240px 宽，和另外 20 条一起刷了一遍」。

##### 三、道理在哪

专家方法论与全部来源链接：`capabilities/image-appeal/methods/expert-playbook.md`。
它不替代判据，但**没有它，判据会被当成仪式照做**。

验收结论写回任务单的 `## 交付` 区块。**生成的图 `synthetic=true`，
不能当产品界面、客户案例或真实记录用**，交付时要写明。

## 边界

- **不做图片编辑。** 局部修改、换背景、涂抹——直说这条线不干这个。
- **示意图不走本线。** 流程图、架构图、时间线、图表走 `capabilities/diagram-production/README.md`——
  它是手写 SVG，不调模型，不花生成费用。把它塞进本线，等于让模型去画流程图。
- **不做视频。** 视频走 `skills/video-pipeline/` 六站，是另一条线，中间没有桥。
- **不自动发布。** 出图和预览是内部动作，发到平台要用户明确授权。
- **不出带文字的图去挂无法证实的主张。** 这是本线的硬线，和文章线同源：
  事实主张必须挂 `fact_ref`，封面文案必须挂 `source_title`，两条路都不许空着走。
- **封面不许无文字。** role 含 `cover` / `封面` 的图必须有 `cover_text`——
  无字封面在一屏几十条的流里不会被任何人看见。
- **不绕过 dry-run。** 用户明确说「直接出」才跳过，跳过时说明会花几张的钱。
- **不把参考图当素材用。** 它只喂测量和出图条件，不拼进任何对外产物——
  参考图多半不是自己拍的，拼进去就是把别人的东西当成自己的发出去。
- **不把量出来的色板自动写进风格库。** 测量不是判断。要不要沉淀成一套新风格，
  由人决定，不由脚本决定。
- **不把吸引力复核交给写简报的人。** `appeal_review.reviewed_by` 必须与 `author` 不同。
  自己写、自己判、自己交付，等于没判。
- **不做风格自动选择。** 脚本给候选，人做选择（宪法 7）。
- **不把未校准的阈值当合格线。** AP-03 的 `calibrated` 还是 false，
  引用它的数字时必须一起说清这一点。
