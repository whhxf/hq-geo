# 文章流水线

## 目的

把 `tasks/<id>.md` 里的一句话，变成能署名发出去的文章，并且每一站都留下可追溯的产出。

这条线只做文章。视频和图片是另外两条流水线，它们共用同一份任务单据和事实上下文，但不共用写作步骤。

## 开始前

完整读取：

- `tasks/<id>.md` — 任务本身，`## 任务` 区块是用户原话，不得改写
- `capabilities/content-production/tasks/README.md` — 状态字段和区块归属的约定
- `capabilities/content-production/strategies/creative-strategies.md` — 结构模式
- `capabilities/content-production/styles/README.md` — 风格示例与风格库
- `00-meta/content-engine/03-platform-hard-rules.md` — 目标渠道的硬规则

**再查一次调研结论库 `research/library/README.md`**——这个主题这个项目**已经调研过什么**。
索引也在项目 `CLAUDE.md` 末尾（每次会话自动加载），但换设备或上下文被压缩后要自己读一次。
**按「覆盖的词」列搜，不要按主题名猜。**

**库里的是平台信号，不是事实**——它告诉你「有人在搜这个、这么问」，不告诉你「事情就是这样」。
**定核心判断（站 3）要用它选方向，但落到稿子里的事实仍走 `skills/sourcing/` 的检索路径。**

涉及品牌或产品推广时，再读 `capabilities/geo/methods/positioning-and-audience.md` 和对应事实包的 `positioning.json`。普通知识内容不强制品牌卡。

## 八站

### 站 1 · 读任务，查事实，定受众坐标

从 `## 任务` 区块提取：想要什么、给谁看、发哪里、手上有什么素材。

然后核对事实包 `facts/`。列出**会影响内容承诺、案例真实性或操作步骤**的缺口。

**定受众坐标。** 品牌/产品内容先看事实包里有没有 `positioning.json`：

- **没有** → 按 `capabilities/geo/methods/positioning-and-audience.md` 建草案（`status: draft`），
  跑 `python3 capabilities/geo/scripts/validate_positioning.py <定位卡路径>`。
  草案里每条定位必须用 `fact_ids` 指向同包 `facts.jsonl`，**不新增事实**
- **有** → 复用，检查 `revision` 是否仍然对应当前事实

定位卡是长期的（对象/受众/场景/问题/优势五个槽位），**但这一篇要单独选定**：主要读者、触发场景、核心问题。
一篇内容只能对准一个人写。选不出来，说明事实不够——登记进缺口，不要硬写。

受众坐标必须能回答四个问题，答不上来就是没定：

| 问题 | 用在哪 |
|---|---|
| 他是谁（决策者还是使用者） | 决定第二人称落在谁身上 |
| 他读到这篇时卡在哪 | 站 3 核心判断的「读者现在以为」 |
| 他读完会做什么 | 决定结尾给什么动作 |
| 他现在相信什么错的 | 站 3 核心判断的「实际上」 |

产出：定位卡 + 缺口清单，写进任务的 `## 待确认` 区块。`stage` 改为 `research`。

### 站 2 · 补料，缺料停机

**一次只问一个最能推进的问题**，不要把所有缺口一次甩出来。

用户回答后按事实包约定补录（`python3 capabilities/fact-packs/scripts/capture_fact.py`），区分企业内部事实、创始人观点、亲历经验和外部事实。外部效果和第三方评价不能仅凭用户回答升级为已验证事实。

素材缺失且无法补齐时，`status` 改为 `blocked`，写明缺什么、缺了会怎样。**不许用模型生成的内容替代真实素材**（宪法第 5 条）。

缺口清零，或用户明确说「就按现有的写」，才进入站 3。

### 站 3 · 定核心判断

用一句话写出这篇文章要让读者相信什么。格式：

> 读者现在以为 ______，实际上 ______，因为 ______。

**三半都从站 1 的受众坐标来，不是临时想的**：前半句是「他现在相信什么错的」，
后半句是「他卡在哪、你要把他带到哪」，「因为」是事实包里的机制。
**没有受众坐标就写不出这一句**——写了也是自说自话，读者认不出来。

这一句是后面所有版本的共同出发点。三条流水线如果同时开工，共享的是这一句和事实上下文，不是正文。

**开头约定**：核心判断的「实际上 ___」必须出现在开头。站 5 写完回头核对一次。

**判断标准有两条，第二条是 2026-09-28 六轮实测补上的。**

**一、只读开头，读者以为这篇文章要讲什么？** 那个答案和核心判断不是同一件事，就是没对齐——后面的内容再好，读者也走不到。

**二、核心判断里的关键词，读者理解的和你说的是不是一回事？**

把每个关键词单独拿出来问：一个没读过前文的人，看到这个词会想到什么？

**实测**：那篇稿子的核心判断是「视频改的不是转化率，是客户『看懂』和『相信』这两步的成本」。
「转化率」作者指的是「询盘除以访客这个比值」，读者读成「客户从看到到下单的整个过程」。
于是这句话被他读成「视频对成交没用」——而下一段又说视频能让人看懂和相信，
**在他看来就是自相矛盾**。两轮独立的读者审计都卡在同一句上，而站 3 原来的检查一条都没拦住：
它只问「判断有没有传出去」，不问「传出去的是不是那个意思」。

产出：每个关键词写一句「读者会怎么理解它」，写进任务的 `## 交付`。
写不出「读者会怎么理解」的词，就是没用读者的话在说话。

产出：核心判断写进任务的 `## 交付` 区块，**等用户确认再往下走**。判断权在人。

### 站 4 · 定结构和风格

**结构**：从策略库按平台和现有素材筛，选 1 个模式（P01—P10）。素材不满足模式的 `required_inputs` 就换一个，不允许为了用某个模式去编素材。用户指定了就用用户指定的。

**风格**：按 `capabilities/content-production/styles/README.md` 生成 3 个候选，写成 `content/styles/<task-id>.html`，让用户打开浏览器看。风格库里已有条目时优先用库里的。

产出：策略 ID 和风格选择，写进任务的 `## 交付` 区块。`stage` 改为 `drafting`。

### 站 5 · 写全文

按选定的结构和风格写。写作逻辑始终是：明确对象 → 用户与场景 → 核心问题 → 有证据的优势 → 适用边界。

**每一段都要能回答：这段是给谁写的、他读完多知道什么。** 答不上来的段落就是凑数。

**写完正文，逐节（按 `##`）写一句「读者获得」：这一节让读者从什么状态到什么状态。**
写不出「到什么状态」的节就是凑数，删掉重写——不要留着等站 6 的读者审计来发现。
这张表写进任务的 `## 交付`，站 6 拿它对照。

**这条不是形式。** 2026-09-28 的实测：一篇稿子事实标注齐全、免责声明到位、三道合规检查全过，
独立读者读完的判词是「**把我劝住了，但没把我劝动**」。写的时候没想过读者读到哪儿会走，
写完也没有任何一道检查会问这件事——**规则写得再对，没有产出物就是空转**。

**事实纪律要求的是「不夸大」，不是「写免责声明」。** 案例、边界、限制这些内容，
标注和读者价值要放在一起——先给读者能用的，来源标注一句带过。
堆三段免责声明，同样是没站在受众角度，只是错得更隐蔽：它看起来完全合规。

写完核对站 3 的开头约定：核心判断的「实际上 ___」在不在开头。

事实只能来自事实包。`needs_confirmation` 的条目写成待确认语气，`prohibited_claim` 不作为正面论据。

**标题。** 正文写完后生成**至少 3 个**候选，每个写明它押的是受众坐标里的哪一项
（他在搜什么 / 他卡在哪 / 他读完能得到什么）。

**关键词原文照抄不算做标题**——那是搜索匹配，不是让人想点。标题要同时满足两件事：
搜索的人认得出来，刷到的人想点进去。三个候选必须是**不同的路线**，不是同一句话换词。

产出：

- 标题：≥3 个候选写进任务的 `## 交付`，站 6 交用户选
- 主稿：`content/packages/<channel>/<idea>/<topic>/article.md`，`<channel>` 是站 2 定的目标渠道
- 其他渠道版本：`content/packages/<channel>/<idea>/<topic>/copy.md`

**渠道未定时用 `blog` 占位，渠道一旦定了就要把稿子移过去**——不要让它留在占位目录里。
路径是渠道的登记处：稿子住在 `blog/` 而实际发头条，系统里就查不到「这篇是给头条的」。

渠道版本从主稿派生，不机械截短，不互相复制格式。目标媒体未知时，媒体包不得标为发布就绪。

### 站 6 · 三道检查

**三道都要做。只做前两道，稿子会变成一份挑不出错、完全合规、但没人读完的文件。**

三道检查的分别：**作者化检查管「像不像 AI」，受众复核管「有没有越界」，读者审计管「读者读不读得下去、拿不拿得走」。**
前两道全是否定式的，而且都是写稿的人自己审自己——它们只能防止变差，不能产生变好。

#### 一、作者化检查

```bash
python3 capabilities/content-production/scripts/check_authorial.py <成稿路径>
```

逐条向用户展示命中，每条只问三个问题：删掉后含义是否变化；能否换成具体动作；能否补事实或条件。

**逐条等用户决定，不要批量改。** 用户说保留就保留——`07` 明确写了，否定词、时间词、范围词和真实的不确定性不得为了降低密度而删除。

改写后对比改写前后：核心判断、数字、专有名词、因果、适用条件、否定和承诺不得漂移（Gate F）。任一变化没有依据就回退。

#### 二、受众复核

作者化检查问的是「像不像 AI」，受众复核问的是「有没有人愿意读」。
**前者全是否定式的——它只能防止变差，不能产生变好。** 只有它不够。

对着站 1 的受众坐标，逐条回答 `positioning-and-audience.md` 的复核清单：

- 读者能否认出自己的问题？
- 是否承诺超过证据？
- 是否把某场景能力写成人人适用？
- 是否丢失限制？

**任何一条答「否」都要指出具体段落并给出改法**，不许只写结论。
尤其检查案例和边界段落：那里最容易退化成免责声明堆叠——合规，但读者一无所获。

#### 三、读者审计

**这一道问的是「读者真的读下去了吗、真的拿走东西了吗」。前两道抓不到这个，因为写稿的人审不出自己的盲区。**

**必须用 Agent 工具起一个独立 agent 执行，不能用写稿的自己审。** 交给它的只有两样：
**成稿全文**和**读者身份**。不要给它任何写作背景——不说为什么这么写、想表达什么、
哪段是重点。它知道得越少，越像真读者。完整提问脚本见
`capabilities/content-production/reader-audit.md`。

六个问题（一个都不能少）：

1. 刷到标题和开头三行，会点进去吗？为什么
2. 读到第几段想退出？哪一句卡住、看不懂、或者觉得是废话
3. **逐节回答**：读完这一节，比读之前多知道了什么（用读者自己的话，不许抄原文）
4. 关掉文章，能跟同行复述出什么
5. 会转给同行吗？什么情况下会、什么情况下不会
6. 读完打算做什么？如果什么都不打算做，说清楚为什么

**逐节对照站 5 的「读者获得」声明。对不上的地方就是要改的地方**——
作者以为给了、读者没拿到，是写法没到位，不是读者没读懂。

**判红标准**（任一条成立就不得进站 7）：

- 有哪一节，读者说不出「多知道了什么」
- 有哪个位置，读者明确说「想退出 / 想跳过 / 是废话」
- 读者读完说不出「打算做什么」
- 读者对某段的理解与站 5 的声明相反

**红了就逐条处理：给改法，或者说明为什么不改。不许只写「保留」。**
处理结果写进任务的 `## 交付`，与站 5 的声明并排放，让人一眼看出哪条对上了、哪条没有。

**这一道的结论不写进定位卡的 `review.status`**——定位卡的 `review` 管的是语义复核
（有没有偷换人群、场景、能力、效果），读者审计是另一回事，各记各的。

答完把结果登记进定位卡的 `applications`：`channel`、`artifact_path`、`audience`、
`scenario`、`problem`、`positioning_revision`、`used_fact_ids`，
以及 `review`（`status` / `reviewer` / `note` / `artifact_sha256`）。
`artifact_sha256` 用 `shasum -a 256 <成稿路径>` 取，成稿改了就要重取。

同时把站 5 的标题候选交给用户选。

产出：用户对每条的决定、读者审计的六问回答与逐条处理、选定的标题、修订后的成稿、更新后的定位卡。`stage` 改为 `review`。

### 站 7 · 写回任务

在 `## 交付` 区块记录：

- 核心判断
- **受众坐标**：这一篇的读者、场景、问题，以及定位卡的 revision
- 策略 ID 和风格选择
- **标题**：选定的那个，以及落选候选和它们各自的路线
- 每个产物的路径和状态
- 作者化检查中用户保留的项和理由
- **受众复核的结论**（四条各是什么，有「否」的写明改了什么）
- 还差什么（如果有）

`stage` 改为 `delivered`，`status` 改为 `done`。

分发是用户的事，分发之后由用户自己填 `## 分发登记`。不要替用户登记，也不要自动发布。

### 站 8 · 写一条学习记录

在**项目根**的 `LEARNING.md` 追加一条：

- **这次**：哪里卡住了、哪个判断被用户改了、哪个做法比预期好
- **下次**：怎么做
- **去向**：`BACKLOG` / `策略库` / `只是记着`

**「去向」是动作，不是分类。** 写 `BACKLOG` 就真的去 `BACKLOG.md` 加一条，写策略库就真的去改对应条目。只记不做，这条记录白写。

**这一站不能跳过。** 前七站产出一篇稿子；站 8 才让这次生产对下次有用。宪法第 7 条要求「每次生产结束必须写回积累，否则这次生产没有产生积累」。

分发数据回来后，用户补了 `## 分发登记`，再追加一条效果记录——那时才第一次能回答「系统有没有用」。

**然后停下。** 后续由用户分发。

## 外部顾问（可选）

某一站你拿不准时，可以问本机装的 dbs（`~/.claude/skills/dbs-*`）。完整清单、边界和禁用项见 `capabilities/content-production/external-advisors.md`。

| 站 | 什么时候问 | 问谁 |
|---|---|---|
| 站 1 | 不确定读者到底要完成什么任务 | `dbs-jtbd` |
| 站 3 | 「因为 ___」这个理由自己不确定 | `dbs-theory-grounding` |
| 站 4 | 不确定开头能不能让陌生人认领 | `dbs-hook` |
| 站 5 | 不确定标题和正文能不能让人读下去 | `dbs-spread`、`dbs-resonate` |
| 站 6 | 怀疑某段论证形式有问题 | `dbs-deconstruct` |

**三条铁律**：调不到就跳过，不停机；它的回答是线索不是依据，不进任务单据；只学做法不搬文本。

**这不是流水线的一站。** 不问也能走完，问了也不改变判断权在用户手里这件事。

## 边界

- 不自动发布，不上传，不产生广告花费。
- 不替用户写 `## 任务` 和 `## 分发登记` 两个区块。
- 不为了让文章显得充实而补事实、补案例、补数据。
- 一次任务只走一条流水线。用户同时要文章和视频时，各自走各自那条，共享站 3 的核心判断。
- 这条线不加载完整 GEO 流程。官网内容、AI 搜索可见性、品牌引用建设走 GEO 分支。
