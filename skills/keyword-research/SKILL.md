# 关键词研究

## 目的

**把「我觉得这个方向行」变成「有证据说明有人在用这种话表达这个需求」。**

```
想法 ──关键词研究──→ 需求簇 + 备选选题 ──登记──→ 选题记录
                                                    ↓
                                            sourcing → brief → 内容
```

它**不产出事实**。事实走 `skills/sourcing/` 的检索路径，进事实包。
这里产出的是**需求信号**：谁在搜什么、用什么话搜、竞争多激烈、他们真正要完成什么任务。

## 开始前

完整读取：

- `capabilities/keyword-research/contracts/research-record.schema.json`
- `capabilities/keyword-research/contracts/demand-cluster.schema.json`
- `capabilities/keyword-research/channels/README.md`
- `capabilities/topic-registry/contracts/topic.schema.json`

再读项目根的 `data/ideas/`、`research/`、`topics/`——**先看这个想法有没有已经做过的调研**，
有就接着做，不重开一轮。

## 站 1：定核心词

从一个想法出发，定一个**核心词**。核心词不是最终的推广词，是这次调研的入口。

> **这一轮要回答的是什么问题？**

- 想知道「有没有人在关心这件事」→ 核心词用**用户会怎么叫它**，不用你内部的叫法
- 想知道「他们到底卡在哪一步」→ 核心词用**任务词**（怎么搭、多少钱、能不能替代）

核心词定错，后面全歪。**定完先给用户看一眼再往下走。**

## 站 2：选渠道

对照 `channels/` 里 `status: verified` 的渠道，选出这次要跑哪几个。

**只选 verified 的。** `unverified` 的渠道进去是试错，不是采集——那种情况明确说「这个渠道我还没跑通过，
这次要去试，可能拿不到东西」，不要假装有把握。

一个渠道能回答的问题不一样：

| 想知道 | 去哪 |
|---|---|
| 有多少人在搜、竞争多激烈、广告主愿出多少钱 | 官方商业工具（`official_commercial`） |
| 用户自己怎么描述这个问题 | 原生内容（`native_content`）：搜索建议、笔记、评论 |
| 这个需求在别的生态里热不热 | 代理信号（`proxy`）——**只能当参考，不能当目标指标** |

**一次跑一个渠道，跑完落盘再跑下一个。** 三个渠道并行会让记录串味。

## 站 3：采集

按渠道文件的「采集步骤」走。用 `web-access` skill 开本机 Chrome（带登录态）。

**每读一个页签，立刻落盘。** 攒到最后会丢。

落盘到 `research/raw/<date>-<channel>-<slug>.json`，按 `research-record.schema.json` 写。

三条纪律：

1. **平台给什么记什么，不改写。** 竞争指数写「高」就记「高」，不换算成数字。
2. **噪音词保留说明。** 平台返回的无关词进 `noise`，写清为什么无关——
   丢掉的话，下次看到同一个词还要重新判断一遍。
3. **口径问题当场记进 `notes`。** 比如「用户路径里的占比是路径内占比，不是全站占比」——
   这类现场发现比任何文档都准。

## 站 4：归一化成需求簇

把原始记录按**用户要完成的任务**聚类，不是按词面相似聚类。

**判断标准**：两个词能不能用同一篇内容回答？能，就是同一个簇。

落盘到 `research/normalized/<date>-<slug>.clusters.json`，按 `demand-cluster.schema.json` 写。

**这一步最容易犯的错是编词。** 校验器会逐词核对——`representative_keywords` 里的每个词，
必须能在 `source_records` 里找到。**代表词不是你想出来的，是从记录里挑出来的。**

**推断词单独放。** 由需求簇推导出来、但平台还没给数据的词，进 `inferred_keywords`，
写清凭什么推出来、要去哪里验证。**它们不能混进代表词**——混进去就是把推断当证据用。

## 站 5：和用户讨论

**这一站不能省。** 需求簇是机器聚出来的，「要不要做、先做哪个」只有用户能定。

给用户看三样：

1. **需求簇**——每个簇一句话说清「谁在什么场景下要完成什么」
2. **排除项**——看过但排除的，写清为什么。**排除项是判断的一部分，不是没看见**
3. **你的判断**——哪个簇最值得做、为什么、风险在哪

然后问**一个问题**：

> 「这几条里，哪一条你手上有别人没有的东西可说？」

**这一问是分水岭。** 答得上来的，才可能变成真选题；答不上来的，做出来也是同质化内容。

## 站 6：登记选题

讨论完产出**备选选题**，写进 `topics/<idea>/topics.json`，按 `topic-registry` 的契约。

**选题必须能回答五问**（见 `capabilities/topic-registry/`）：

1. 谁在什么场景下遇到什么问题？
2. 现有解释或做法哪里失效？
3. 你有什么不同判断或可展示证据？
4. 内容承诺是什么，看完能得到什么？
5. **这个承诺如何被证伪？**

**答不上第 5 问的不是选题，是想法。** 想法留在 `data/ideas/`，不进选题记录。

新登记的选题 `state` 是 `candidate`。**选定哪条由用户说，不由系统推荐。**

## 收尾

给用户三样：

1. **这次调研发现了什么**——一句话，不是复述表格
2. **哪些还不能用**——推断词、没跑通的渠道、未知的量级
3. **下一步**——选定某条就进 `skills/sourcing/` 立 brief；不选就把选题留在记录里

## 边界

- **不产出事实。** 平台信号不是事实，不能进事实包。要事实走 `sourcing` 的检索路径。
- **不做跨平台加总。** 小红书的 370 和抖音的 370 不是一回事。`AGENTS.md` 第 61 行是硬线。
- **不把推断当证据。** 推出来的词标清楚是推出来的。
- **不替用户选选题。** 系统给证据和判断，选定哪条是用户的决定。
- **不跳过站 5。** 没有讨论就直接登记的选题，五问里至少三问答不上来。

## 和相邻能力的分工

| 谁 | 回答什么 |
|---|---|
| **本 skill** | 平台上真实的人在搜什么、用什么话、要完成什么任务 |
| `skills/geo-research/` | AI 搜索里的问题模型：Query Fan-Out、竞品占位、内容空白 |
| `skills/sourcing/` 检索路径 | **这条内容里的事实从哪来**——一手来源、三级定级 |
| `capabilities/topic-registry/` | 选题的登记与准入（五问） |
